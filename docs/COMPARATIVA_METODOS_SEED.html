Fechas

El historial se generaba en Python y se guardaba con fechas absolutas. Al mes siguiente, la demo mostraba un dashboard de hace un mes: había que volver a correr el generador para «refrescarlo».

Todo se calcula con CURRENT_DATE en el momento de ejecutar: 

date_trunc('month', CURRENT_DATE)
  - make_interval(months => n)

24 meses siempre terminando hoy, se corra cuando se corra.
Contraseñas

El SQL traía las claves en claro y Python las hasheaba después con hash_password(). Un paso más que podía fallar, quedar a medias o no correrse.

El hash bcrypt ya está escrito en el SQL, listo para insertar: 

'$2b$12$TJrykEFiGHr649wpNCuh…'

23 líneas con hash en 02: ninguna clave viaja en claro.
Triggers de auditoría

El seed insertaba con los triggers activos y cada fila quedaba registrada como si fuera una acción humana. Resultado real:

7.644 transacciones 5.914 auditoría

Se apagan por tabla, dentro de la misma transacción: 

ALTER TABLE orden_trabajo
  DISABLE TRIGGER USER;

DISABLE TRIGGER USER apaga solo los de usuario: las claves foráneas siguen activas, así que un dato mal referenciado sigue fallando.

Resultado: 0 + 0 filas de ruido.

2 Qué hace cada archivo, y por qué importa

Un archivo monolítico mezcla tres cosas que cambian a ritmos distintos. Separarlas es lo que permite re-aplicar solo la capa que hace falta.

01

01_estructura.sql — el portero

88 líneas · 4,2 KB

Verifica las precondiciones: que exista la extensión vector (la necesita el RAG) y que el esquema esté migrado con Alembic. Si falta algo, falla de inmediato y con un mensaje claro.

Por qué importa

Es el archivo que evita el clásico «corrí el seed y quedó a medias»: si la base no está migrada, no se inserta nada, en lugar de insertar medio catálogo contra un esquema viejo y dejar el error escondido tres tablas más adelante.

02

02_maestros.sql — el catálogo

541 líneas · 27,4 KB

Todo lo que cambia poco y a lo que la operación hace referencia:

3 empresas (con RUT)
25 usuarios (7 roles)
6 plantas · 11 disciplinas

28 sensores

Por qué importa

Es la fuente de verdad de identidad: los códigos de máquina (CHA-001, MOL-001…) y los emails son la clave con la que la operación, la topología y los tests se referencian. Si esto cambia, cambia todo: por eso vive solo y es idempotente por RUT, email y código.

Por qué importa

Aquí están las 8 apariciones de CURRENT_DATE y los DISABLE TRIGGER USER sobre 9 tablas. Es el archivo que hace que el gráfico de 24 meses nunca quede viejo y que la auditoría no se llene de basura.

Cómo se ejecuta ahora

Antes

python scripts/seed.py
  → aplica seed_data.sql
  → aplica seed_multiempresa.sql
  → poblar_historial()  # generador
  → hash_password()     # claves
  → crea admin@barb.com

Ahora

python scripts/seed.py
  → 01_estructura.sql
  → 02_maestros.sql
  → 03_operativos.sql

Y si no hay Python a mano, funciona igual con psql -f.

3 · Conclusión

El método nuevo garantiza que la demo se vea profesional sin importar cuándo se ejecute.

Con el método anterior, el estado de la demo dependía de cuándo se había generado el historial y de que Python hubiera hecho su parte. Con tres archivos SQL que se calculan al ejecutarse, el resultado es el mismo hoy, en un mes o en el día de la presentación: la ventana de 24 meses termina siempre en la fecha en que se corre el seed.

Nunca se ve vieja

CURRENT_DATE en las fechas: el dashboard de «últimos 24 meses» siempre tiene datos frescos.

Nunca se ve sucia

0 filas en transacciones y auditoria_cambio: los reportes no muestran actividad fantasma.

Nunca se ve falsa

Equipos, manuales y disciplinas reales: si alguien pregunta «¿qué es ese equipo?», hay un manual que lo respalda.

Y además: se puede correr dos veces

Los tres archivos son idempotentes: se apoyan en claves naturales (RUT, email, código de máquina, numero_ot). Una segunda corrida no duplica nada. Se verificó: dos ejecuciones seguidas dejan exactamente los mismos conteos.

Lo único que sigue necesitando Python es el envoltorio que recorre los tres archivos; el contenido de los datos ya no depende de él. La base se puede reconstruir desde cero con alembic upgrade head y tres psql -f.
