Vista general

BARB es una plataforma multiempresa de mantenimiento industrial: órdenes de trabajo (OT), dashboard de KPIs, topología de plantas, avisos de falla y un asistente de IA con RAG sobre los documentos de cada empresa. Monorepo con dos proyectos independientes, sin build compartido.

Decisiones de diseño

Decisiones de arquitectura que condicionan cómo se escribe y se opera BARB.

Sin ORM en runtime
SQL crudo con %(name)s y dict_row. SQLAlchemy solo existe como dependencia de desarrollo para Alembic.
Sesión nunca confiada al cliente
Cada dependencia re-resuelve el rol desde la tabla sesion con el token Bearer.
Multiempresa por diseño
Todo dato se filtra por empresa_id; el cliente nunca decide el alcance (salvo super_usuario).
Backend decide, frontend refleja
El backend devuelve allowed_transitions por OT según rol; el frontend no duplica reglas.
Hard lock de OT en IA
El modelo no tiene herramienta de escritura de OT: propone, y el código resuelve la confirmación del usuario.
RBAC fail-closed en el chat (HU-24)
Solo supervisor recibe la tool proponer_ot; el gate re-verifica el rol antes de crear.
Contexto persistente en BD (HU-22)
El historial se lee de chat_session.messages en cada turno. LangGraph sin checkpointer: no crea tablas extra y sirve con varios workers.
Parámetros por modelo
MODEL_SETTINGS separa temperatura y max tokens de texto y multimodal.
Esquema solo por migraciones
Alembic con un único head; nada de DDL en handlers. Migrar Supabase antes de hacer merge a main.
Infra tolerante
Redis, Supabase Storage y embeddings son opcionales; sin ellos hay degradación controlada (503 / full-text).
Sin scheduler en proceso
Render free duerme: los jobs corren por cron externo (GitHub Actions) contra un endpoint idempotente.
Estado en memoria, un proceso
OtEventBroker y limitadores viven en RAM. Escalar horizontalmente exige Redis.

Backend

FastAPI + Uvicorn, psycopg3 async con AsyncConnectionPool, configuración con pydantic-settings (src/barb/core/config.py, lee .env). Gestor de paquetes: uv.

Convenciones

  • Conexiones del pool siempre liberadas vía context manager (nunca conn.close()).
  • Sin @lru_cache en endpoints de catálogo; dependencias de permisos realmente async.
  • Alias de rutas conservados por compatibilidad: /api/work-orders y /api/work_orders, /auth/login y /api/auth/login.
  • El esquema vive solo en migraciones Alembic; nunca se crea en handlers.

Aislamiento por empresa

  • OT derivan empresa por orden_trabajo → maquina → planta.empresa_id.
  • Documentos, chunks y chat llevan empresa_id propio.
  • Búsqueda RAG siempre filtrada por empresa_id y activo = TRUE.
  • Las tools del chat fijan la empresa al construirse y re-verifican el rol (no pasan por dependencias FastAPI).
  • max_usuarios se aplica por empresa; estado active | suspended | cancelled.

Órdenes de trabajo

Cierre en dos pasos (migración 0014). Sin transición directa in_progress → completed. Comentario obligatorio al cancelar o devolver.

Máquina de estados

pending ─┐
assigned ├──► in_progress ──► por_validar ──► completed   (final)
overdue ─┘        │                │  └──────► in_progress (devolución, con comentario)
                  │                └─────────► cancelled
                  └──────────────────────────► cancelled   (final, con comentario)

pending | assigned | overdue ──► cancelled
  • Cada estado destino mapea a una acción en ACCIONES; el backend filtra allowed_transitions por rol.
  • Pasar a por_validar: técnico asignado o supervisor (enviar_a_validacion). Validar: solo supervisor (validar_ot).
  • Endpoint: PATCH|PUT /api/work-orders/{numero_ot}/status.

Tiempo real (SSE, HU-10)

  • OtEventBroker en memoria: fan-out por empresa, buffer de 500 eventos para Last-Event-ID, evento resync si hay hueco/desborde.
  • work_orders llama a publish_safe(...) tras commit en crear / cambiar estado / eliminar.
  • Stream: GET /api/work-orders/stream con Bearer o ?ticket= de un solo uso (POST …/stream/ticket).
  • El router realtime se registra antes que work_orders para que /stream no caiga en /{numero_ot}.
  • Limitación: un solo proceso. Escalar implicaría Redis pub/sub.

Asistente de IA y RAG

Chat sobre LangGraph (HU-26) con recuperación de documentos de la empresa y skills/tools construidas por request.

Grafo del chat

gate_otresuelve en código si el usuario confirma una OT propuesta
retrievepgvector o full-text por empresa_id (+ maquina_id)
generate ⇄ toolsLLM con tools crear_tools(empresa_id, usuario_id, rol)
propuestatermina el turno con texto exacto de proponer_ot

Tools del modelo

  • consultar_ots_maquina, proponer_ot, listar_maquinas_planta, actualizar_parametros_maquina (SLA/costo), proponer_planta_completa.
  • Hard lock (CGBIDA-476): el modelo no tiene tool para escribir OT; crear_ot_aprobada no es una tool.
  • RBAC fail-closed (HU-24): proponer_ot solo se registra para supervisor; el prompt omite la regla de creación para otros roles y crear_ot_aprobada re-verifica el rol en el gate.
  • Asignación: técnico que chatea se asigna a sí mismo; supervisor/admin → primer técnico activo de la empresa; sin técnicos, se bloquea. Máquinas con fuzzy match (bom001 = BOM-001).
  • La propuesta caduca si la conversación avanza; ventana anti-duplicados de 10 min.

RAG

Ingesta
Extracción de texto (pdf/docx/txt/md/csv/json/log) → chunks ~1000 chars → documento_chunk. Embeddings best-effort al subir (scripts/backfill_embeddings.py para rellenar).
Recuperación
Similitud pgvector (search_similar_chunks, <=> sobre documento_embedding, 0003). Fallback a full-text spanish (search_chunks) si no hay proveedor, falla o la tabla está vacía.
Máquina por conversación (HU-23)
chat_session.maquina_id (0016) y documento.maquina_id. Primero docs de la máquina, relleno con generales de la empresa. Ficha bloque_equipo en el prompt.
Multimodal
POST /api/chat/multimedia. Turnos con imagen se persisten con has_image: true (la imagen no). Prompt exige respuestas concisas con **negritas**.
Memoria y modelos (HU-22)
Historial en chat_session.messages (JSONB), guardado en el finally del stream con asyncio.shield. MODEL_SETTINGS define parámetros de texto y multimodal.

Proveedores

  • LLM vía LangChain: llm_provider ∈ deepseek / openai / openrouter / groq / nvidia, con llm_fallback_providers opcional.
  • Embeddings: NVIDIA nvidia/nemotron-3-embed-1b, 2048 dims; la key cae a NVIDIA_API_KEY.
  • Documentos en Supabase Storage; sin SUPABASE_URL/SUPABASE_SERVICE_ROLE_KEY los endpoints responden 503.
  • Límites por usuario: tasa de chat y tokens diarios (en memoria).

Restricciones y reglas de integridad

  • Roles: ck_usuario_rol_valido limita usuario.rol a operador, tecnico, supervisor, engineer, gerente, admin, super_usuario. ck_usuario_empresa_rol: empresa_id NULL solo para super_usuario.
  • Aviso de falla: estado ∈ pendiente | con_ot | descartado; descartar exige motivo_descarte; resolver exige resuelto_por y resuelto_en; los 4 campos de foto van todos nulos o todos presentes.
  • Notificaciones: frecuencia diaria | semanal, hora 0–23, dia_semana 0–6 y obligatorio si es semanal.
  • Aislamiento: documento_chunk.empresa_id duplicado a propósito (filtro de tenant sin join + barrera extra). Las OT derivan empresa por orden_trabajo → maquina → planta → empresa.
  • Borrado: cascada en dependientes (ot_foto, ot_repuesto, ot_audit_log, documento_chunk, documento_embedding, sesion, lectura_sensor, zonas/conexiones); SET NULL en vínculos opcionales (chat_session.maquina_id, documento.maquina_id, transacciones.usuario_id).
  • Índices destacados: GIN sobre documento_chunk.tsv (full-text español, columna generada) · HNSW sobre documento_embedding.embedding::halfvec(2048) · ix_ot_abiertas_vencimiento (OT abiertas por vencimiento) · índices por (empresa_id, fecha DESC) en bitácoras.
  • Triggers: trg_transaccion (por fila, tablas de negocio → transacciones) y trg_auditar_usuario/empresa/orden_trabajo (→ auditoria_cambio). El usuario llega por app.usuario_id.

auditoria_cambio.registro_id y usuario_id son referencias lógicas sin FK, para conservar el historial aunque el registro se borre. Las tablas heredadas del esquema inicial (reporte, sesion_debug, diagnostico, programa_mantenimiento, system_audit_log…) siguen en el esquema; su uso activo en la API es el descrito en las otras pestañas.

Despliegue y operación

Producción separada en tres proveedores gratuitos; local con Docker solo para Postgres.

Cloudflare PagesFrontend Angular (Node 24 en build). CORS permite el dominio de Pages.
RenderBackend FastAPI definido en render.yaml. Free tier duerme.
SupabasePostgres (pooler de transacciones, puerto 6543) + Storage de documentos.
GitHub ActionsCron externo del job de OT atrasadas.

Orden al cambiar el esquema

  1. Aplicar la migración a Supabase.
  2. Recién entonces hacer merge a main.

Los pushes a main no ejecutan migraciones (DEPLOY.md §2.4). Pool ajustado para el cierre por inactividad del pooler de Supabase (PR #50).

Limitaciones de escala conocidas

  • OtEventBroker, rate_limit y token_limit viven en memoria: válidos solo con un proceso. Para escalar, mover a Redis (pub/sub y contadores).
  • Sin scheduler interno: depende de cron externo.
  • Redis y Storage opcionales; endpoints dependientes responden 503 sin configuración.
